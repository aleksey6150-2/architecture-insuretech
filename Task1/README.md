# Task1. Проектирование технологической архитектуры InsureTech

## Цель

Спроектировать целевую технологическую архитектуру приложения InsureTech с учётом планируемого роста пользователей в регионах РФ и требований бизнеса к отказоустойчивости.

## Исходные требования

Бизнес предъявляет следующие требования к системе:

- сервис должен работать 24/7;
- сервис должен обслуживать пользователей из всех часовых поясов РФ;
- доступность приложения должна быть не ниже 99,9%;
- RTO — 45 минут;
- RPO — 15 минут;
- время загрузки страниц должно быть примерно одинаковым для пользователей из разных регионов и не должно зависеть от географического положения пользователя;
- текущий объём данных — около 50 GB.

Сейчас система хранит:

- базовую информацию о клиентах: ФИО, контакты, документы;
- информацию о страховых продуктах и тарифах;
- историю заявок клиентов.

## Краткое описание целевого решения

Для InsureTech предлагается отказоустойчивая архитектура с основной и резервной площадками.
Основная площадка работает в режиме active и принимает пользовательский и партнёрский трафик. Резервная площадка работает в режиме warm standby и готова принять трафик в случае отказа основной площадки.
Для ускорения загрузки страниц web-приложение выносится в Object Storage и раздаётся через CDN. Backend-сервисы разворачиваются в Kubernetes с горизонтальным масштабированием и распределением реплик по зонам доступности.
PostgreSQL переводится из одиночного экземпляра в HA-конфигурацию: primary + synchronous replica в основной площадке и asynchronous replica в резервной площадке. Также используется резервное копирование, WAL archiving и PITR.

## Масштабирование

### Выбранная стратегия

Для backend-сервисов выбрано горизонтальное масштабирование.

Горизонтально масштабируются следующие сервисы:
- `core-app`;
- `client-info`;
- `ins-product-aggregator`;
- `ins-comp-settlement`.

Для каждого stateless-сервиса предполагается запуск нескольких реплик в Kubernetes. Масштабирование выполняется с помощью HPA.

Также используется Cluster Autoscaler, который добавляет worker nodes при нехватке ресурсов в кластере.

### Почему горизонтальное масштабирование эффективнее

Горизонтальное масштабирование лучше подходит для этой системы, потому что:

- приложение уже развёрнуто в Kubernetes;
- backend-сервисы можно запускать в нескольких репликах;
- нагрузка будет расти неравномерно, особенно после рекламных кампаний;
- несколько реплик повышают отказоустойчивость;
- отказ одного pod или worker node не приводит к полной недоступности сервиса.

Вертикальное масштабирование также может использоваться, но как вспомогательная мера. Например, для PostgreSQL или для изменения размеров worker nodes. Однако для backend-приложений вертикальное масштабирование хуже решает задачу отказоустойчивости, потому что один крупный инстанс всё равно остаётся точкой отказа.

## Зоны доступности и площадки

Для выполнения требований по доступности и восстановлению используется несколько зон доступности.

Целевая конфигурация:

- основная площадка — active;
- резервная площадка — warm standby;
- основная площадка содержит Kubernetes-кластер, распределённый по нескольким зонам доступности;
- резервная площадка содержит отдельный независимый Kubernetes-кластер.

Такой подход позволяет переживать отказы отдельных узлов, зон доступности и всей основной площадки.

## Kubernetes

### Выбранный подход

Для Kubernetes выбраны независимые кластеры:

- `prod-k8s` — основной кластер;
- `dr-k8s` — резервный кластер.

Растянутый Kubernetes-кластер между основной и резервной площадками не используется.

### Почему не используется растянутый кластер

Растянутый кластер между площадками усложняет архитектуру и эксплуатацию. Он создаёт дополнительные зависимости от межплощадочной сети и повышает риск split-brain-сценариев.

Независимые кластеры лучше подходят для disaster recovery, потому что:

- уменьшают blast radius;
- проще управляются;
- позволяют независимо обновлять и восстанавливать площадки;
- лучше изолируют отказ основной площадки от резервной;
- проще соответствуют active-passive failover-стратегии.

### Конфигурация приложений в Kubernetes

Для критичных backend-сервисов используется следующая конфигурация:

- минимум 2–3 реплики каждого сервиса;
- HPA для автоматического масштабирования;
- Cluster Autoscaler для масштабирования worker nodes;
- readiness probes;
- liveness probes;
- Pod anti-affinity для распределения реплик по разным узлам и зонам;
- PodDisruptionBudget для защиты от потери доступности при обновлениях и обслуживании кластера.

## Балансировка нагрузки

Балансировка нагрузки выполняется на нескольких уровнях.

### Глобальный уровень

На глобальном уровне используется DNS failover.

Единый домен приложения указывает на основную площадку. DNS failover выполняет health checks публичных endpoints основной и резервной площадок.

В штатном режиме трафик направляется на основную площадку. Если health check основной площадки становится неуспешным, DNS переключает пользователей на резервную площадку.

На схеме отражены следующие проверки:

- health check primary ALB;
- health check DR ALB.

### Уровень площадки

Внутри площадки используется Application Load Balancer или Ingress Controller.

Он принимает внешний трафик и маршрутизирует его в Kubernetes на соответствующие backend-сервисы.

На этом уровне используются:

- health checks до ingress endpoints;
- readiness probes для проверки готовности pod принимать трафик;
- liveness probes для автоматического перезапуска неработающих pod.

## Фейловер-стратегия

Для системы выбрана стратегия active-passive, также называемая warm standby.

### Штатный режим

В штатном режиме:

- основная площадка обслуживает весь пользовательский и партнёрский трафик;
- резервная площадка находится в режиме готовности;
- приложения в резервном кластере могут быть запущены в минимальном количестве реплик;
- база данных реплицируется из основной площадки в резервную;
- резервные копии и WAL-архивы сохраняются в Object Storage.

### Аварийный режим

При отказе основной площадки:

1. Health check фиксирует недоступность primary ALB или ingress endpoint.
2. DNS failover переключает трафик на резервную площадку.
3. PostgreSQL asynchronous replica в резервной площадке повышается до primary.
4. Сервисы в резервном Kubernetes-кластере масштабируются до рабочего количества реплик.
5. Пользовательский и партнёрский трафик начинает обслуживаться через DR site.

### Соответствие требованиям RTO и RPO

RTO 45 минут достигается за счёт того, что резервная площадка уже развёрнута и находится в состоянии warm standby.

RPO 15 минут достигается за счёт:

- потоковой репликации PostgreSQL;
- регулярной архивации WAL;
- резервного копирования;
- возможности восстановления через PITR.

## Конфигурация базы данных

### Целевая конфигурация PostgreSQL

Вместо одиночного экземпляра PostgreSQL используется HA-кластер.

Конфигурация:

- PostgreSQL Primary в основной площадке;
- PostgreSQL Synchronous Replica в другой зоне доступности основной площадки;
- PostgreSQL Asynchronous Replica в резервной площадке;
- резервные копии в Object Storage;
- WAL archive;
- PITR.

### Репликация

Внутри основной площадки используется синхронная репликация между primary и standby-репликой. Это повышает устойчивость к отказу отдельной ВМ или зоны доступности.

Между основной и резервной площадками используется асинхронная репликация. Она позволяет поддерживать актуальную копию данных в DR site и выполнять требование RPO 15 минут.

### Резервное копирование

Для восстановления данных используется:

- регулярное полное резервное копирование;
- архивация WAL;
- Point-in-time recovery.

Backups и WAL-архивы хранятся в Object Storage.

## Шардирование базы данных

Шардирование базы данных не применяется.

Причины:

- текущий объём данных составляет около 50 GB;
- этот объём не требует горизонтального разделения данных;
- шардирование значительно усложнит архитектуру, эксплуатацию и восстановление;
- шардирование усложнит транзакционность и согласованность данных;
- текущие требования лучше закрываются HA-репликацией, резервным копированием и масштабированием приложений.

На текущем этапе достаточно PostgreSQL HA cluster с репликацией и PITR.

## Обеспечение одинакового времени загрузки страниц

Чтобы время загрузки страниц не зависело от региона пользователя, статические ресурсы web-приложения выносятся из backend-контура.

Frontend-сборка React-приложения размещается в Object Storage и раздаётся через CDN.

Через CDN доставляются:

- HTML;
- CSS;
- JavaScript;
- изображения;
- другие статические ресурсы.

Такой подход позволяет отдавать статический контент с edge-узлов, расположенных ближе к пользователям, и снижает зависимость времени загрузки страницы от географии.

Backend API продолжает обслуживаться через DNS failover, ALB и Kubernetes.

## Мониторинг и эксплуатация

Для обеспечения эксплуатации 24/7 в архитектуру добавляется мониторинг и алертинг.

Необходимо собирать:

- availability;
- latency;
- error rate;
- CPU и memory по pod и node;
- состояние Kubernetes workloads;
- состояние PostgreSQL primary и replicas;
- replication lag;
- состояние backup jobs;
- успешность health checks;
- количество HTTP 5xx и 4xx ошибок.

Алерты должны срабатывать раньше, чем проблему заметят пользователи.

Такое решение соответствует требованиям бизнеса:

- доступность 99,9%;
- RTO 45 минут;
- RPO 15 минут;
- готовность к росту нагрузки;
- работа 24/7;
- одинаковая скорость загрузки страниц для пользователей из разных регионов РФ;
- отсутствие single point of failure на уровне приложения и базы данных.
