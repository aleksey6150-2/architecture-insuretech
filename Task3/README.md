# Task3. Переход на Event-Driven архитектуру

## Цель

Спроектировать переход части взаимодействий InsureTech на Event-Driven архитектуру, чтобы снизить связность сервисов, уменьшить зависимость от синхронных REST-вызовов и подготовить систему к подключению новых страховых компаний.

## Текущие проблемы

В текущей архитектуре `core-app` и `ins-comp-settlement` получают данные о продуктах и тарифах через REST API сервиса `ins-product-aggregator`.

`ins-product-aggregator` при каждом запросе обращается ко всем страховым компаниям, агрегирует ответы и возвращает результат синхронно.

Также `ins-comp-settlement` раз в сутки обращается в `core-app`, чтобы получить список оформленных за день страховок.

Такая схема создаёт риски:

- высокая связность сервисов;
- зависимость внутренних сервисов от внешних API страховых компаний;
- рост latency при увеличении количества страховых компаний;
- риск timeout и ошибок при синхронных вызовах;
- ночная пакетная нагрузка на `core-app`;
- риск рассинхронизации локальных реплик данных;
- сложность масштабирования.

## Целевое решение

В целевой архитектуре добавляется брокер сообщений:

- Kafka;
- или Managed Service for Apache Kafka;
- или другой совместимый event streaming broker.

Через брокер сообщений распространяются события:

- об изменении продуктов и тарифов;
- об оформлении страховых полисов.

Декомпозиция функциональности между сервисами при этом не меняется.

## Новые event-driven взаимодействия

### 1. Обновление продуктов и тарифов

Сервис `ins-product-aggregator` продолжает отвечать за интеграцию со страховыми компаниями и агрегацию данных о продуктах.

Но вместо того чтобы `core-app` и `ins-comp-settlement` периодически запрашивали полный список продуктов по REST, `ins-product-aggregator` публикует события в брокер сообщений.

События:

- `ProductCreated`;
- `ProductUpdated`;
- `ProductDeleted`;
- `TariffUpdated`.

Topic:

- `insurance-products`.

Потребители:

- `core-app`;
- `ins-comp-settlement`.

Оба сервиса продолжают хранить локальные реплики данных о продуктах и тарифах, но теперь обновляют их через поток событий.

### 2. Передача оформленных страховок в settlement

Сервис `core-app` при успешном оформлении страховки публикует событие `PolicyCreated`.

Topic:

- `policies`.

Потребитель:

- `ins-comp-settlement`.

`ins-comp-settlement` сохраняет полученные события в свою БД и использует эти данные для формирования реестра взаиморасчётов со страховыми компаниями.

Таким образом, ночной REST-запрос из `ins-comp-settlement` в `core-app` больше не нужен.

## Что остаётся синхронным

Не все взаимодействия нужно переводить на события.

Синхронными остаются:

- взаимодействие frontend с `core-app`;
- взаимодействие `core-app` с `client-info` при пользовательских сценариях;
- взаимодействие `core-app` с платёжным сервисом;
- взаимодействие `ins-product-aggregator` со страховыми компаниями.

Для внешних интеграций со страховыми компаниями необходимо добавить:

- timeout;
- retry with exponential backoff;
- circuit breaker;
- bulkhead;
- dead letter queue;
- мониторинг ошибок и latency.

## Transactional Outbox

В целевой архитектуре используется паттерн Transactional Outbox.

Он нужен для того, чтобы изменение данных в БД и публикация события в брокер происходили надёжно.

### Outbox в core-app

`core-app` использует Transactional Outbox при оформлении страховки.

В одной транзакции сервис:

1. сохраняет данные о полисе в свою БД;
2. сохраняет событие `PolicyCreated` в outbox-таблицу.

После этого отдельный publisher читает outbox-таблицу и публикует событие в topic `policies`.

Это защищает систему от ситуации, когда полис был создан, но событие о нём не было отправлено.

### Outbox в ins-product-aggregator

`ins-product-aggregator` использует Transactional Outbox при обновлении продуктов и тарифов.

В одной транзакции сервис:

1. сохраняет новое состояние продуктов и тарифов в свою БД;
2. сохраняет события `ProductUpdated` и `TariffUpdated` в outbox-таблицу.

Отдельный publisher публикует эти события в topic `insurance-products`.

## Consumer-side обработка

Потребители событий должны быть идемпотентными.

Это значит, что повторная обработка одного и того же события не должна приводить к некорректному состоянию данных.

Для этого можно использовать:

- уникальный `eventId`;
- версию сущности;
- `updatedAt`;
- таблицу обработанных событий;
- upsert-операции при обновлении локальных реплик.

## Topics

### insurance-products

Назначение:

- распространение данных о продуктах и тарифах.

Producer:

- `ins-product-aggregator`.

Consumers:

- `core-app`;
- `ins-comp-settlement`.

Примеры событий:

- `ProductCreated`;
- `ProductUpdated`;
- `ProductDeleted`;
- `TariffUpdated`.

### policies

Назначение:

- передача данных об оформленных страховках.

Producer:

- `core-app`.

Consumer:

- `ins-comp-settlement`.

Примеры событий:

- `PolicyCreated`;
- `PolicyCancelled`;
- `PolicyUpdated`.

## Dead Letter Queue

Для обработки ошибок создаются DLQ topics.

Примеры:

- `insurance-products.dlq`;
- `policies.dlq`.

Если consumer не может обработать событие после нескольких повторов, событие отправляется в DLQ для последующего анализа и ручной или автоматической переобработки.

## Ожидаемый эффект

Переход на Event-Driven архитектуру позволит:

- снизить количество синхронных REST-вызовов между сервисами;
- убрать polling продуктов и тарифов;
- уменьшить зависимость `core-app` и `ins-comp-settlement` от доступности `ins-product-aggregator`;
- убрать ночную пакетную нагрузку на `core-app`;
- ускорить распространение изменений тарифов;
- повысить устойчивость к ошибкам внешних API страховых компаний;
- подготовить систему к подключению новых страховых компаний;
- повысить масштабируемость решения.

## Итог

В целевой архитектуре не меняется декомпозиция сервисов, но меняется способ взаимодействия между ними.

REST остаётся для пользовательских и командных синхронных операций.

Event Streaming используется для распространения изменений состояния:

- продукты и тарифы;
- оформленные страховки.

Для надёжной публикации событий используется Transactional Outbox.
