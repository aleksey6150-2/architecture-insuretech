# Task3. Анализ проблем и рисков текущей архитектуры

## Контекст

Сервисы `core-app` и `ins-comp-settlement` получают данные о доступных страховых продуктах и тарифах через REST API сервиса `ins-product-aggregator`.

Сервис `ins-product-aggregator` при вызове синхронно обращается ко всем страховым компаниям, агрегирует ответы и возвращает единый список продуктов.

Сейчас интеграция выполняется с пятью страховыми компаниями. В ближайшее время планируется подключить ещё пять страховых компаний, то есть количество внешних интеграций увеличится до десяти.

Также `ins-comp-settlement` раз в сутки обращается в `core-app` по REST API, чтобы получить список всех оформленных за день страховок для формирования реестра взаиморасчётов.

## Проблемы текущей архитектуры

### 1. Синхронная зависимость от страховых компаний

`ins-product-aggregator` в момент REST-запроса обращается ко всем страховым компаниям. Если хотя бы одна страховая компания отвечает медленно или возвращает ошибку, это влияет на время ответа всего запроса.

При увеличении количества страховых компаний с пяти до десяти вероятность задержек и ошибок возрастает.

Риски:

- рост latency;
- timeout при запросе продуктов;
- нестабильное время ответа;
- деградация пользовательского опыта;
- рост количества ошибок между сервисами.

## 2. Рост нагрузки на ins-product-aggregator

Сервис `core-app` запрашивает данные о продуктах раз в 15 минут, а `ins-comp-settlement` — раз в сутки. Каждый такой запрос может приводить к обращению сразу ко всем страховым компаниям.

При увеличении количества страховых компаний нагрузка на `ins-product-aggregator` и внешние API возрастёт.

Риски:

- сервис становится узким местом;
- увеличивается потребление CPU, memory и сетевых ресурсов;
- повышается вероятность отказов;
- становится сложнее гарантировать SLA.

## 3. Polling вместо событийной модели

`core-app` и `ins-comp-settlement` получают обновления продуктов и тарифов через периодические REST-запросы.

Такой подход приводит к следующим проблемам:

- данные обновляются с задержкой;
- сервисы вынуждены регулярно выполнять запросы даже при отсутствии изменений;
- невозможно эффективно распространять изменения сразу после их появления;
- увеличивается связность сервисов.

## 4. Дублирование логики получения справочных данных

`core-app` и `ins-comp-settlement` оба получают данные из `ins-product-aggregator` и поддерживают локальные реплики продуктов и тарифов.

Проблема не в наличии локальных реплик, а в способе их обновления. Сейчас обновление зависит от синхронного REST API и расписания запросов.

Риски:

- рассинхронизация данных;
- задержки обновления тарифов;
- ошибки при обновлении локальных реплик;
- сложность диагностики проблем.

## 5. Ночная пакетная интеграция ins-comp-settlement с core-app

`ins-comp-settlement` раз в сутки запрашивает в `core-app` все оформленные за день страховки.

Это создаёт следующие проблемы:

- высокая нагрузка на `core-app` в момент ночной выгрузки;
- риск timeout при большом количестве оформленных страховок;
- повторная выгрузка может приводить к дублированию данных;
- `ins-comp-settlement` зависит от доступности `core-app` в момент формирования реестра;
- при росте бизнеса объём выгрузки будет увеличиваться.

## 6. Риск потери данных при публикации событий без Transactional Outbox

При переходе к Event-Driven архитектуре появляется риск несогласованности между изменением состояния в БД и публикацией события.

Например:

- полис успешно создан в БД `core-app`;
- после этого сервис падает до отправки события `PolicyCreated`;
- `ins-comp-settlement` не получает информацию об оформленной страховке.

Чтобы избежать такого сценария, необходим паттерн Transactional Outbox.

## 7. Недостаточная устойчивость к ошибкам внешних API

Интеграции со страховыми компаниями могут быть нестабильными. При росте числа партнёров увеличивается вероятность:

- timeout;
- HTTP 5xx;
- rate limit со стороны страховой компании;
- неполных или некорректных ответов;
- временной недоступности API.

Без retry policy, circuit breaker и DLQ такие ошибки будут напрямую влиять на внутренние сервисы InsureTech.

## Риски при росте количества страховых компаний

После подключения ещё пяти страховых компаний количество внешних вызовов увеличится в два раза. При сохранении синхронной модели это приведёт к следующим рискам:

- увеличение среднего и p95/p99 времени ответа;
- рост количества ошибок;
- рост нагрузки на `ins-product-aggregator`;
- ухудшение доступности сервисов, которые зависят от агрегатора;
- усложнение поддержки локальных реплик продуктов и тарифов;
- увеличение нагрузки на `core-app` при ночных выгрузках для settlement.

## Вывод

Текущая архитектура использует синхронные REST-взаимодействия там, где лучше подходит событийная модель.

Для устранения проблем рекомендуется:

1. Перевести распространение данных о продуктах и тарифах на Event Streaming.
2. Перевести передачу оформленных страховок из `core-app` в `ins-comp-settlement` на события.
3. Использовать брокер сообщений.
4. Использовать паттерн Transactional Outbox в сервисах, которые изменяют данные и публикуют события.
5. Добавить retry, timeout, circuit breaker, bulkhead и DLQ для интеграций со страховыми компаниями.
